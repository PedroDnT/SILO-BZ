| 2026-08-31 | claude/code-review-k7hw45            | **v1.1.** Four silent data-loss bugs found and fixed, all the same class — a unique key documented as intentional while `ON CONFLICT DO UPDATE` discarded the rest (it keeps the last-written row; it does not aggregate). (1) Historical CDA collapsed 11 of 12 months per year for 2005–2022: `ingest_fi_hist_cda` passed `month=1` for a yearly archive that holds twelve competency months, so every pre-2023 year held January alone. Fixed (`month=None` derives each row's period from its own DT_COMPTC) and backfilled. (2) `cvm_fip_periodic` keyed on `period_year` while DT_COMPTC sat unread in `raw`, so a yearly FIP file kept one filing per fund per year — measured 72–77% lost on the real 2015/2022/2025 files; new key `(cnpj, doc_type, period, classe_cota, row_hash)`, migration 34. (3) The CDA holdings keys were too narrow (395 collisions in 2005); widened with `tp_fundo`/`tp_negoc`, migration 33. (4) NOT fixed, the user's call: `cvm_fi_cda` discards **80.4%** of BLC_1 — 257 government bonds collapse onto one row, R$261.6M true vs R$39.3M stored. The fix is an additive `cvm_fi_cda_titpub` keyed on the security (~98.8% retention), never a rekey of `cvm_fi_cda`, which would change its grain and break every consumer. Written up in `docs/DATA_INVENTORY.md` §2. **The schema gate went down twice** and took every ingest job with it: `schema.sql` runs BEFORE the migrations and `CREATE TABLE IF NOT EXISTS` is a no-op on an existing table, so an index over a migration-added column failed with `column "tp_fundo" does not exist`. Both fresh-database verifications passed — that is precisely why they missed it. `tests/test_schema_upgrade_path.py` now asserts statically that every indexed column is reachable from `schema.sql` alone on an existing database, and CI grew an upgrade-path fixture that rewinds a seeded database and replays the current schema. **New data:** CDA block 6 debentures (`cvm_fi_cda_debentures`, migration 35) — the fund→corporate-credit edge, keyed `(fund, month, issuer, maturity, …, row_hash)` after an audit on both file eras showed a natural key alone loses 15.8%; 253,563 source rows → 253,563 stored, verified end to end. **New serving:** `api.fund_holdings` (catalog v17) answers both directions — what a fund holds, and which funds hold a ticker — returning rows as filed and never summing across application types. **API/SDK correctness:** three SDK methods sent parameter names the SQL functions do not declare (`p_underlying` vs `p_prefix`; `p_codneg` vs `p_ticker` twice) and could only ever 404; `tests/test_sdk_rpc_params_match_sql.py` now joins the two sides by AST. `api.option_exercises` is tier-capped (500/5000) instead of a `LIMIT 5001` sentinel no caller could observe past PostgREST's 1000-row cap. **close_adj:** still `adjusted=false` and no factor guessed. Diagnostic 11 proved the inputs exist (1,382 share-count events, 705 with both sides of the tape), and migration 36's `(isin, trade_date)` index makes the verification query answerable at all — it had been silently skipped on every health run for exceeding 90 s. Also: SDK 0.2.0 (truncation detection via `Content-Range`, `SiloTimeout`, bearer-token tier), `serve/` returns JSON on every error path, and **`docs/DATA_INVENTORY.md`** — what we ingest, what we could ingest and don't, what we ingest and don't serve, and the serving grain per family. |
