### Overview

*Termo* is B3's forward market: a trade agreed today for settlement a fixed number of days out. It rides the same COTAHIST tape as [`quotes`](/api-docs/quotes) under **`tpmerc` = `030`**, and it is a small segment — on the order of a hundred prints per session against tens of thousands of options.

Everything is unadjusted; every row carries `adjusted: false`.

<Warning>
  **The grain is `(codneg, trade_date, term_days)`.** One code can print several terms in the same session — a 30-day and a 60-day forward on the same paper are different contracts at different prices. A query that ignores `term_days` sees what looks like duplicate dates.

  **There is no `underlying` column**, for the same reason as [options](/api-docs/options): the codneg root usually names the underlying paper, but B3 publishes no mapping, and deriving one would be inventing an identity join.
</Warning>

### `POST /rpc/termo_history`

One code's daily prints over a window.

```sql
api.termo_history(p_codneg TEXT,
                  p_from   DATE DEFAULT CURRENT_DATE - 365,
                  p_to     DATE DEFAULT CURRENT_DATE)
```

`p_codneg` is the termo negotiation code, e.g. `PETR4T`, upper-cased server-side. [`lookup`](/api-docs/lookup) does **not** resolve termo codes and nothing enumerates them, so you must already know it. Probing is safe: a code with no prints returns `200 []`.

| Column | Type | Meaning |
| --- | --- | --- |
| `codneg` | text | Negotiation code. Part of the grain. |
| `trade_date` | date | Session date. Part of the grain. |
| `term_days` | text | COTAHIST `prazot` — the contract's term in days. **Text**, as stored. Part of the grain. |
| `spec` | text | Paper specification (`especi`). |
| `currency` | text | Defaults to `R$` when the source leaves it blank. |
| `open` / `high` / `low` / `average` / `close` | numeric | Session prices. Unadjusted. |
| `bid` / `ask` | numeric | Best bid and ask at close. |
| `trades` | integer | Number of trades. |
| `quantity` | numeric | Quantity traded, exactly as COTAHIST publishes it. |
| `volume` | numeric | Financial volume in BRL. |
| `isin` | text | ISIN as published. |
| `quotation_factor` | integer | COTAHIST `fator_cotacao`. |
| `adjusted` | boolean | Always `false`. |
| `source` | text | `b3_cotahist`. |

Ordered by `trade_date`, then `term_days` shortest-first — sorted by length then as text, so `30` precedes `60` precedes `120` without a numeric cast that could fail on malformed source data.

**Note**: one 1,000-row page, and it refuses above it (`22023`). Because several terms can print per session, a busy code reaches the page faster than a cash ticker. There is **no cursor** — narrow the window and call again.

### Termo in `panel`

[`panel`](/api-docs/panel) accepts termo codnegs for `close` and `volume`, as `id_type` `termo` / `asset_class` `derivative`. But a panel row is one value per `(id, date, metric)`, and termo's real grain has `term_days` in it — so when several terms print in one session the panel keeps the **shortest term** and drops the rest, rather than averaging them into a number nobody quoted. For anything term-aware, use `termo_history`.

`close_return` is not offered for termo (or options) — it accepts `ticker` ids only.

### Empty and error behavior

- **Unknown code → `200 []`.** Never a fabricated price.
- **Known code, no prints in the window** → also `200 []`. Termo is thin; a code can go days without a print, and a quiet window is indistinguishable from a wrong code. Check [`coverage`](/api-docs/coverage)'s `derivatives` row.
- A malformed date returns `400`.
