### Overview

`coverage` answers one question: **how far does the data actually go?** Call it before reporting a "latest" figure, before reading an empty result as a fund that stopped filing, and before treating a series as up to date.

One row per dataset, plus one `funds_<family>` row per fund family — the families file on different cadences and one blended date misreads all of them. No arguments.

```sql
api.coverage()
```

### The four dates mean four different things

Reading one for another is the most common coverage mistake.

| Column | Means |
| --- | --- |
| `as_of` | The newest period that has landed **and has actually elapsed** — freshness, bounded by today. Null means the dataset is empty, which is a real answer. |
| `complete_through` | The newest period classified **complete** — what the default windows serve. `null` for `financials`: no completeness model exists for company filings, and a fabricated date is the claim this function exists to prevent. |
| `newest_period` | The newest period **key** present, unbounded. Can sit in the future — FIP is keyed 31-December, so a filing arriving in March carries `2026-12-31`. **Never read as freshness.** |
| `landed_at` | When ingest last **succeeded**, from the `cvm_ingest_log` audit trail. Only `status = 'ok'` runs with a finish time count, so a run in flight has not landed and a later failed run never advances it. Null when none is recorded. |
| `landed_git_sha` | **Which code produced this data**: the git commit of the very run that set `landed_at`, recorded from `GITHUB_SHA`. Null when that run recorded none (a run before catalog v34, or one started outside GitHub Actions); it is **never borrowed** from an older run, because an older run's code did not produce the newest rows. |

`landed_at` answers "is the pipeline healthy"; `as_of` answers "how far does the data go". A `landed_at` days old with a current `as_of` means ingest stopped but the data it left is fine. `landed_git_sha` answers "which code wrote it": diff it against a fix you are waiting on to know whether the newest rows were parsed before or after it. The audit log behind it also records a `parser_version`, bumped only when a parser or field map changes what a stored value means; it is not served here.

### Datasets

- **`quotes`** — the most recent B3 cash session, across all tickers and boards.
- **`funds`** — the most recent filing period in the fund registry.
- **`fund_nav`** — the most recent period in the monthly fundamentals fact.
- **`derivatives`** — the most recent session across options and termo (`tpmerc` `070`, `080`, `030`).
- **`financials`** — the newest reference date any ITR/DFP filing has reached, read from the filing index, not the 31M-row account table.
- **`anbima_classes`** — the newest boletim reference month.
- **`fidc_cedentes` / `fidc_sacados` / `fidc_sectors` / `fidc_scr`** — the newest month landed per [FIDC concentration](/api-docs/fidc) tab; `notes` states where each starts (tab I's cedente slots 2019-11, tab X 2023-10).
- **`fidc_tranches` / `fidc_aging`** — the newest month landed for the [FIDC tranche and aging](/api-docs/fidc-structure) tabs; `notes` states that both begin in **2025-01** because CVM publishes no archive of them — an upstream limit, not a gap.
- **`fnet_documents`** — the [FNET document register](/api-docs/fnet-documents) behind `fund_documents` and `fund_restatements`, keyed on the **delivery day**: `as_of` is the newest delivery day held, `complete_through` the day before it. `notes` states that history begins at Silo's first crawl or backfill, and that fund links come from a fortnightly sweep, so the newest documents may have no cnpj yet. `landed_at` is the register crawl alone.
- **`inflation`** — the newest month of headline IPCA (SGS 433) held; the cores, classifications and groups publish the same day. `landed_at` is the SGS ingest alone, never a PTAX or Focus run.
- **`company_events`** — the newest IPE delivery date held for [company events](/api-docs/company-events); `complete_through` is null (no completeness model covers company filings). `notes` states that history starts in 2015 and that filings CVM published without a protocol number are not held. `landed_at` is the IPE ingest alone.
- **`macro_series`** — the newest elapsed observation of any of the nine [macro series](/api-docs/macro); `newest_period` can sit in the future because the Selic target is published ahead. `landed_at` is the SGS ingest.
- **`ptax`** — the newest PTAX business day held; `landed_at` is the PTAX ingest alone, never an SGS run.
- **`inflation_items`** — the newest month of IBGE's item tree held; `notes` states the 2020-01 structure change (SIDRA 7060 replaced 1419, item codes changed, `item_number` is the continuity).

**Not covered**: `fund_holdings` and `fund_debentures` have no row yet — read the newest `period` off the rows themselves.

`notes` carries a caveat the dates cannot, and is null on rows that have none. Rows carrying one today: `funds_fidc` (the 2025-01 delinquency regime break), `funds_fip` (why `newest_period` runs ahead of the calendar), `fund_nav` (pointing at `catalog().applicability`), the four FIDC concentration rows, the two FIDC structure rows (history begins 2025-01), the five B3 lending / flow rows (the ratchet), the two inflation rows (which column is derived, and the 2020-01 SIDRA structure change), `company_events` (history from 2015, protocol-less filings not held), and `macro_series` / `ptax` (units and cadences).

### Notes

- **The dates are supposed to differ.** B3 quotes arrive daily; CVM publishes fund filings on a one-to-two month lag. A `fund_nav` date two months behind `quotes` is normal, not a broken pipeline.
- **Read the `funds_<family>` rows before a window claim.** `complete_through` is what an omitted `p_to` clamps to. `funds` and `fund_nav` carry the blended value — the *most lagging* family's bound.
- **`derivatives` and `quotes` are reported separately** though they come from the same COTAHIST file: the segments can land independently. Check `derivatives` before claiming an option chain is current.
- **`fund_nav.as_of` is a month key** — `2026-06-01` means the June 2026 period, not the first of June.
- **These are maxima across a whole dataset**, not per-instrument. An individual fund can be months behind while still filing normally — use [`fund_profile`](/api-docs/funds)'s `last_period`.
- **A window past a dataset's `as_of` is not an error.** It returns nothing for the months that do not exist yet; the API will not extend a series to reach the date you asked for.

### Regime boundaries

`complete_through` tells you where a series ends; it cannot tell you where one **changes meaning**. That is `notes`, and machine-readably `catalog().regime_breaks` (dataset, column, boundary, before, after, never).

The boundary on the books today is FIDC `delinquency` — absent from CVM's pre-2025 monthly file, present on every row from 2025-01. Chain-linking a level or a change across it manufactures a move the fund never made. Check it before differencing any fund series, the way you check `complete_through` before a window claim.

### metric_coverage

`coverage` answers *how fresh is this dataset*. `metric_coverage` answers **does this family file this metric at all, and since when?**

```bash
curl -s -X POST "$SILO_URL/rest/v1/rpc/metric_coverage" \
  -H "apikey: $SILO_ANON_KEY" -H "Content-Type: application/json" -d '{}'
```

```json
[
  { "entity_type": "fidc", "metric": "delinquency",
    "first_period": "2025-01-31", "last_period": "2026-08-31",
    "filed_rows": 73259, "total_rows": 178928 },
  { "entity_type": "fidc", "metric": "nav",
    "first_period": "2019-01-31", "last_period": "2026-08-31",
    "filed_rows": 178928, "total_rows": 178928 }
]
```

| Field | What to know |
| --- | --- |
| `first_period` / `last_period` | Oldest and newest periods carrying a **non-null** value for that pair. |
| `filed_rows` / `total_rows` | How dense the pair is. `filed_rows` well below `total_rows` means the metric is filed *sometimes* — different from *always*, different again from never. |

**Note**: an absent pair is not-applicable, not late. Only pairs with at least one filed value appear — `("fip", "quotaholders")` is missing because FIP never files it, not because the data has yet to arrive. Listing it with null dates would read as a gap. Use `metric_coverage` rather than inferring a start date from nulls in a series, which is how a format change gets read as a credit event.

Measured off the warehouse on every refresh, which is why `catalog().metrics.<m>.coverage` points here rather than carrying a date.

### Errors

There are no arguments to get wrong. `401` means the key headers are missing; `404` (`PGRST202`) means you sent arguments to a function that takes none.
