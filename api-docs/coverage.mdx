### Overview

`coverage` answers one question: **how far does the data actually go?** Call it before reporting a "latest" figure, before reading an empty result as a fund that stopped filing, and before treating a series as up to date.

One row per dataset, plus one `funds_<family>` row per fund family — the families file on different cadences and one blended date misreads all of them. No arguments.

```sql
api.coverage()
```

### Response

| Field | Type | Meaning |
| --- | --- | --- |
| `dataset` | text | `quotes`, `funds`, `fund_nav`, `derivatives`, `financials`, `anbima_classes`, `fidc_cedentes`, `fidc_sacados`, `fidc_sectors`, `fidc_scr`, or `funds_<family>`. |
| `as_of` | date | The newest period that has landed **and has actually elapsed** — freshness, bounded by today. Null means the dataset is empty, which is a real answer. |
| `complete_through` | date | The newest period classified **complete** — what the default windows serve. `null` for `financials`: no completeness model exists for company filings. |
| `newest_period` | date | The newest period **key** present, unbounded. Can sit in the future. **Never read as freshness.** |
| `landed_at` | timestamptz | When ingest last **succeeded**, from `cvm_ingest_log`. Only `status = 'ok'` runs count, so a failed run never advances it. Null when none is recorded. |
| `source` | text | `b3_cotahist`, `cvm`, or `anbima`. |
| `notes` | text | A caveat the dates cannot carry. Null on rows with none. |

Datasets in detail:

- **`quotes`** — the most recent B3 cash session, across all tickers and boards.
- **`funds`** — the most recent filing period in the fund registry.
- **`fund_nav`** — the most recent period in the monthly fundamentals fact.
- **`derivatives`** — the most recent session across options and termo (`tpmerc` `070`, `080`, `030`).
- **`financials`** — the newest reference date any ITR/DFP filing has reached, read from the filing index.
- **`anbima_classes`** — the newest boletim reference month.
- **`fidc_cedentes` / `fidc_sacados` / `fidc_sectors` / `fidc_scr`** — the newest month landed per [FIDC concentration](/api-docs/fidc) tab; `notes` states where each starts.

**Not covered**: `fund_holdings` and `fund_debentures` have no row yet — read the newest `period` off the rows themselves.

Three rows carry a `notes` today: `funds_fidc` (the 2025-01 delinquency regime break), `funds_fip` (why `newest_period` runs ahead of the calendar), and `fund_nav` (pointing at `catalog().applicability`).

### Notes

- **The dates are supposed to differ.** B3 quotes arrive daily; CVM publishes fund filings on a one-to-two month lag. A `fund_nav` date two months behind `quotes` is normal, not a broken pipeline.
- **Read the `funds_<family>` rows before a window claim.** `complete_through` is what an omitted `p_to` clamps to. `funds` and `fund_nav` carry the blended value — the *most lagging* family's bound.
- **`derivatives` and `quotes` are reported separately** though they come from the same COTAHIST file: the segments can land independently. Check `derivatives` before claiming an option chain is current.
- **`fund_nav.as_of` is a month key** — `2026-06-01` means the June 2026 period, not the first of June.
- **These are maxima across a whole dataset**, not per-instrument. An individual fund can be months behind while still filing normally — use [`fund_profile`](/api-docs/funds)'s `last_period`.
- **A window past a dataset's `as_of` is not an error.** It returns nothing for the months that do not exist yet; the API will not extend a series to reach the date you asked for.
- **`landed_at` answers "is the pipeline healthy"; `as_of` answers "how far does the data go".** A `landed_at` days old with a current `as_of` means ingest stopped but the data it left is fine.

### Regime boundaries

`complete_through` tells you where a series ends; it cannot tell you where one **changes meaning**. That is `notes`, and machine-readably `catalog().regime_breaks` (dataset, column, boundary, before, after, never).

The boundary on the books today is FIDC `delinquency` — absent from CVM's pre-2025 monthly file, present on every row from 2025-01. Chain-linking a level or a change across it manufactures a move the fund never made. Check it before differencing any fund series.

### metric_coverage

`coverage` answers *how fresh is this dataset*. `metric_coverage` answers **does this family file this metric at all, and since when?**

```bash
curl -s -X POST "$SILO_URL/rest/v1/rpc/metric_coverage" \
  -H "apikey: $SILO_ANON_KEY" -H "Content-Type: application/json" -d '{}'
```

```json
[
  { "entity_type": "fidc", "metric": "delinquency",
    "first_period": "2025-01-31", "last_period": "2026-08-31",
    "filed_rows": 73259, "total_rows": 178928 },
  { "entity_type": "fidc", "metric": "nav",
    "first_period": "2019-01-31", "last_period": "2026-08-31",
    "filed_rows": 178928, "total_rows": 178928 }
]
```

| Field | Meaning |
| --- | --- |
| `first_period` / `last_period` | Oldest and newest periods carrying a **non-null** value for that pair. |
| `filed_rows` / `total_rows` | How dense the pair is. `filed_rows` well below `total_rows` means the metric is filed *sometimes* — different from *always*, different again from never. |

**Note**: an absent pair is not-applicable, not late. Only pairs with at least one filed value appear — `("fip", "quotaholders")` is missing because FIP never files it. Use `metric_coverage` rather than inferring a start date from nulls in a series.

Measured off the warehouse on every refresh, which is why `catalog().metrics.<m>.coverage` points here rather than carrying a date.

### Errors

There are no arguments to get wrong. `401` means the key headers are missing; `404` (`PGRST202`) means you sent arguments to a function that takes none.
