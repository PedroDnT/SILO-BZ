`coverage` answers one question: **how far does the data actually go?** One row per
dataset (`quotes`, `funds`, `fund_nav`, `derivatives`, `financials`, `anbima_classes`)
plus one `funds_<family>` row for each fund family that has data — so the row count
grows with coverage rather than being fixed. No arguments, no filters.

```sql
api.coverage()
```

Call it before reporting a "latest" figure, before deciding an empty result means a fund
stopped filing, and before treating a series as up to date. It is the only endpoint that
tells you where the warehouse ends — the others just return fewer rows.

## Parameters

None. Send an empty JSON body.

## Returns

One row per dataset, plus one `funds_<family>` row per fund family (`funds_fi`,
`funds_fidc`, `funds_fii`, `funds_fip`, `funds_fiagro`), because the families file on
different cadences and one blended date misreads all of them:

<ResponseField name="dataset" type="text">
  `quotes`, `funds`, `fund_nav`, `derivatives`, `financials`, `anbima_classes`, or
  `funds_<family>`.

  - **`quotes`** — the most recent B3 cash session stored, across all tickers and boards.
  - **`funds`** — the most recent filing period in the fund registry, across all vehicles.
  - **`fund_nav`** — the most recent period in the monthly fundamentals fact.
  - **`derivatives`** — the most recent session stored across options and termo
    (`tpmerc` `070`, `080`, `030`).
  - **`financials`** — the newest reference date any listed-company filing (ITR/DFP)
    has reached, read from the filing index, not the 31M-row account table.
  - **`anbima_classes`** — the newest boletim reference month.

  Not covered: **holdings and debentures** (`fund_holdings`, `fund_debentures`) have no
  row yet — read the newest `period` off the rows themselves until one exists.
</ResponseField>
<ResponseField name="as_of" type="date">
  The newest period that has landed **and has actually elapsed** — freshness, bounded by
  today. **Nullable** — a null means the dataset is empty, which is a real answer, not an
  error.

  It is bounded on purpose. A period key is not a statement about elapsed time: FIP files
  annually keyed to 31-December, so a filing that arrives in March carries the period
  `2026-12-31`. Before v25 the blended `funds.as_of` read `2026-12-31` in September, and
  an agent reading it as freshness believed it had the fourth quarter. The forward-dated
  key is still published, as `newest_period`.
</ResponseField>
<ResponseField name="complete_through" type="date">
  The newest period classified **complete** — what the default windows actually serve.
  It diverges from `as_of` exactly where the filing cadence makes the newest period
  partial: an in-progress month, a family under CVM's 1–2 month publication lag, or
  FIP's annual year-end row (its `as_of` is a Dec-31 date even when perfectly
  current — read `complete_through`, not staleness, for FIP). Equal to `as_of` for
  data that is complete by construction (`quotes`, `derivatives`, `anbima_classes` — a
  session print and a published boletim edition are whole when they land); the
  family-blended value for `funds` and `fund_nav`; and **`null` for `financials`** on
  purpose — no completeness model exists for company filings, and a fabricated date is
  exactly the claim this endpoint exists to prevent.
</ResponseField>
<ResponseField name="newest_period" type="date">
  The newest period **key** present, which can sit in the **future** — this is the raw
  maximum, unbounded. For `funds_fip` it is a year-end date; for every dataset that files
  in arrears it equals `as_of`. **Never read this as freshness**: it tells you the newest
  label in the warehouse, not that the period has happened.
</ResponseField>
<ResponseField name="landed_at" type="timestamptz">
  When ingest last **succeeded** for that source, from the `cvm_ingest_log` audit trail —
  a wall-clock time, not a period. Only runs with `status = 'ok'` **and** a finish time
  count, so a run still in flight has not landed and a later *failed* run never advances
  it. **Nullable** when no successful run is recorded yet.

  This is the column that answers "is the pipeline healthy" as opposed to "how far does
  the data go". A `landed_at` days old with a current `as_of` means ingest has stopped but
  the data it left behind is still fine.
</ResponseField>
<ResponseField name="source" type="text">
  `b3_cotahist` for quotes and derivatives, `cvm` for the fund and company datasets,
  `anbima` for the class benchmarks.
</ResponseField>
<ResponseField name="notes" type="text">
  A caveat the two dates cannot carry. **Nullable** — null on every row that has none.
  Today three rows carry one: **`funds_fidc`** states the 2025-01 `delinquency` regime
  break (null on every row before it, filed on every row after it — never chain-link
  through it), **`funds_fip`** explains why its `newest_period` runs ahead of the
  calendar, and **`fund_nav`** points at `catalog().applicability` and
  [`metric_coverage`](#metric-coverage).
  Read it before differencing any fund series; the same boundaries are machine-readable in
  `catalog().regime_breaks`.
</ResponseField>

The `funds_<family>` rows are the ones to read before a window claim:
`complete_through` is the latest period that family has **fully** filed, which is
what an omitted `p_to` clamps to. `funds` and `fund_nav` carry the blended value
(`latest_complete_period(NULL)`), which is the *most lagging* family's bound.

## Reading it

<Note>
  **The dates are supposed to differ.** B3 quotes arrive daily; CVM publishes fund
  filings on a one-to-two month lag. A `fund_nav` date two months behind `quotes` is the
  normal state of the world, not a broken pipeline.
</Note>

- `derivatives` and `quotes` come out of the same COTAHIST file but are reported
  separately, because the segments can land independently — a day where only the cash rows
  parsed leaves `derivatives` a session behind. Check this row, not `quotes`, before
  claiming an option chain is current.
- `fund_nav.as_of` is a **month key** — `2026-06-01` means the June 2026 filing period, not
  the first of June.
- A `panel` request whose window extends past a dataset's `as_of` is not an error; it simply
  returns nothing for the months that do not exist yet. That is the intended behavior — the
  API will not extend a series with a repeated last value to reach the date you asked for.
- These are **maxima across the whole dataset**, not per-instrument. An individual fund can
  be months behind the aggregate `as_of` while still filing normally. Use
  [`fund_profile`](/api-docs/funds)'s `last_period` for a single vehicle.

## Regime boundaries

`complete_through` tells you where a series ends; it cannot tell you where a series
**changes meaning**. That is what `notes` is for. A boundary is recorded when the source
format changed such that the same column means something different on either side — the
one on the books today is FIDC `delinquency`, absent from CVM's pre-2025 monthly file and
present on every row from 2025-01. Chain-linking a level or a change across such a
boundary manufactures a move the fund never made. The list is machine-readable as
`catalog().regime_breaks` (dataset, column, boundary, before, after, never); check it
before differencing any fund series, the way you check `complete_through` before a
window claim. Details on the FIDC case: [`fund_nav`](/api-docs/funds#which-columns-each-family-files).

## metric_coverage

`coverage` answers *how fresh is this dataset*. `metric_coverage` answers a different
question: **does this family file this metric at all, and since when?**

```bash
curl -s -X POST "$SILO_URL/rest/v1/rpc/metric_coverage" \
  -H "apikey: $SILO_ANON_KEY" -H "Content-Type: application/json" -d '{}'
```

```json
[
  { "entity_type": "fidc", "metric": "delinquency",
    "first_period": "2025-01-31", "last_period": "2026-08-31",
    "filed_rows": 73259, "total_rows": 178928 },
  { "entity_type": "fidc", "metric": "nav",
    "first_period": "2019-01-31", "last_period": "2026-08-31",
    "filed_rows": 178928, "total_rows": 178928 }
]
```

<ResponseField name="first_period / last_period" type="date">
  The oldest and newest periods carrying a **non-null** value for that pair.
</ResponseField>
<ResponseField name="filed_rows / total_rows" type="bigint">
  How dense the pair is: `filed_rows` counts the rows where the metric is present,
  `total_rows` every row of that family in the window. `filed_rows` well below
  `total_rows` means the metric is filed *sometimes*, which is different from filed
  *always* and different again from never.
</ResponseField>

<Note>
  **An absent pair is not-applicable, not late.** Only pairs with at least one filed
  value appear. `("fip", "quotaholders")` is missing because FIP never files it — the
  column is null by construction, exactly as `catalog().applicability` says — not because
  the data has yet to arrive. Listing it with null dates would read as a gap, so it is
  omitted instead.
</Note>

This is measured off the warehouse on every refresh, not written down once. That is why
`catalog().metrics.<m>.coverage` points here rather than carrying a date: the one
exception is `delinquency`, whose `since` is a published regime boundary with its own
test. Use `metric_coverage` instead of inferring a start date from nulls in a series —
inferring is how a format change gets read as a credit event.

## Errors

There are no arguments to get wrong. A `401` means the anon key headers are missing; a
`404` (`PGRST202`) means you sent arguments to a function that takes none.
