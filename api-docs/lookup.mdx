`lookup` turns something a human typed into something [`panel`](/api-docs/panel),
[`quotes`](/api-docs/quotes), or [`funds`](/api-docs/funds) will accept. It searches three
populations at once — B3 tickers, CVM funds, and listed companies — and returns whatever
matched, tagged with the key that matched it.

```sql
api.lookup(p_query TEXT)
```

<Note>
  **Parameters, response columns and types are generated** from the SQL catalog and render
  under **Endpoints → Lookup** in the sidebar. This page carries what a schema cannot: what
  the matching actually does, and which columns are null on purpose.
</Note>

<Warning>
  **It does not invent identifier matches.** There is no ticker ↔ CNPJ join here. If a query
  matches both a ticker and a listed company, you get two rows and it is your call whether
  they are the same entity. A confident-looking cross-reference we cannot prove is exactly
  the kind of fabrication this API refuses to make.
</Warning>

## How `p_query` matches

Matching differs by population, and the difference is the whole behaviour of the endpoint:

| Population | Matching |
| --- | --- |
| Ticker | **exact**, upper-cased and trimmed — no substring search |
| ISIN | **exact**, upper-cased and trimmed |
| CNPJ | non-digits stripped, then **exact**; works for funds and listed companies |
| `cd_cvm` | **exact**, against the CVM company code |
| Fund or company name | case-insensitive **substring** |

<Note>
  Because names match as substrings, an empty string or a single common letter matches nearly
  every fund and company, and you get an arbitrary 20 of them. Send something specific.
</Note>

## Field notes

Only the columns that need explaining. The full list is in the generated endpoint page.

| Field | What to know |
| --- | --- |
| `id_type` | `ticker`, `cnpj`, or `cd_cvm` — this is what tells you *which endpoint* will accept the `id` beside it. |
| `asset_class` | Three different vocabularies in one column: the conservative B3 cash type for tickers (`equity`, `unit`, `bdr`, `fund_quota`, `cash_security`), the fund's `entity_type` for funds (`fi`, `fidc`, `fii`, `fip`, `fiagro`), and `cia` for listed companies. |
| `name` | Nullable for funds whose registry name we do not hold — a null name is a missing registry row, not a missing fund. |
| `isin` | Tickers only. Null on fund and company rows by construction. |
| `cnpj` | **Always null on ticker rows.** Again: no invented ticker-to-issuer match. Populated for funds and companies. |
| `tickers` | A listed company's active B3 trading codes, from CVM's **published** FCA valores-mobiliários filing (`cia_ticker`) — never matched by name. Populated on `cia` rows only; null on fund and ticker rows, and null for a company with no active published listing. |

The CNPJ and the ticker arrive on the same CVM row, so nothing in `tickers` is inferred:

```json
{ "id_type": "cd_cvm", "id": "9512", "name": "PETROLEO BRASILEIRO SA PETROBRAS",
  "cnpj": "33000167000101", "tickers": ["PETR3", "PETR4"], "isin": null }
```

<Warning>
  **Not every listed company has a published ticker map.** `lookup('ITUB4')` returns only a
  ticker row, with `cnpj` and `tickers` both null — so `financials('ITUB4')` resolves nothing
  and answers `200 []`. When a ticker gives you no company row, resolve by company name or
  `cd_cvm` instead.
</Warning>

## Example

<CodeGroup>

```bash curl
curl -s -X POST "$SILO_URL/rpc/lookup" \
  -H "apikey: $SILO_ANON_KEY" \
  -H "Content-Type: application/json" \
  -d '{"p_query":"PETR4"}'
```

```python Python
rows = requests.post(
    f"{URL}/rpc/lookup", headers=H, json={"p_query": "PETR4"}
).json()
```

```javascript JavaScript
const { data } = await supabase.rpc('lookup', { p_query: 'PETR4' })
```

</CodeGroup>

```json
[
  { "id": "PETR4", "id_type": "ticker", "asset_class": "equity",
    "name": "PETROBRAS", "isin": "BRPETRACNPR6", "cnpj": null }
]
```

A name query spans populations:

```json
[
  { "id": "12345678000190", "id_type": "cnpj", "asset_class": "fidc",
    "name": "EXAMPLE FIDC MULTISETORIAL", "isin": null, "cnpj": "12345678000190" },
  { "id": "01234", "id_type": "cd_cvm", "asset_class": "cia",
    "name": "EXAMPLE PARTICIPACOES S.A.", "isin": null, "cnpj": "98765432000110" }
]
```

## Limits and ordering

- **At most 20 rows**, across all three populations combined.
- **No defined ordering.** If more than 20 rows match, which 20 you receive is arbitrary and
  may change between calls. Narrow the query rather than paging — there is no offset that
  would help.
- Ticker rows span every cash-market BDI board, including BDR and fund-quota boards.

## Empty results

No match returns `200 []`. That means the string did not match any ticker, ISIN, CNPJ,
`cd_cvm`, fund name, or company name we hold — not that the entity does not exist. Check
spelling, then [`coverage`](/api-docs/coverage) to confirm the dataset is loaded.
