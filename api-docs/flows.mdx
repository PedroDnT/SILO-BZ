### Overview

`investor_flow` answers one question: **what did each class of investor do on a given session?** Foreign investors, institutionals, individuals and the rest, bought and sold, in R$ thousands.

| Endpoint | Grain | What it holds |
|---|---|---|
| `GET /investor_flow` | `(investor_type, reference_date)` | Daily buy / sell / net flow, plus the month-to-date figures it was derived from |

A **view**: `GET`, PostgREST filters, `limit`/`offset` paging. The securities-lending views are on [Securities lending](/api-docs/lending).

<Warning>
  **These numbers are a first difference that SILO computes. B3 does not publish a daily flow series.** B3 publishes a **month-to-date cumulative snapshot**, released at **T+2**. Two failure modes are handled here rather than left to you:

  - **The difference never reaches across a month boundary.** The window is partitioned by month, so January's last snapshot can never be subtracted from February's first.
  - **The first snapshot held for a month is not always that month's first session.** It counts as a daily flow only when it really is; otherwise the flow is `null` and `flow_basis` says why.

  The series therefore has genuine holes near the start of any month SILO began capturing mid-way through. They are marked, not filled.
</Warning>

<Warning>
  **History starts at first capture and cannot be extended backwards.** `b3_investor_participation` is part of B3's BDI group — roughly 21 business days of retention, no archive. Do not read the first date as a market event, and do not compute a long-run average until the warehouse has held that much.

  The T+2 lag also means `as_of` trails the calendar by two sessions **even when ingest is healthy**. `landed_at` is the column that answers "did the pipeline run?".
</Warning>

### `GET /investor_flow`

| Param | Meaning |
| --- | --- |
| `investor_type` | `eq.<type>`, exactly as B3 publishes it. Read the distinct values off the data rather than hard-coding a translation. |
| `reference_date` | `eq.2026-09-16`, or `gte.` / `lte.`. The session the flow is **for**, not the date B3 published it. |
| `flow_basis` | `eq.delta`, `eq.month_open`, `eq.unknown_opening_snapshot`. |
| `select` / `order` / `limit` | Column list, sort, page size (capped at 1,000). |

#### Read `flow_basis` before anything else

<Warning>
  **Rows the view cannot interpret carry `null` flows — never zeros — and summing them as zeros silently understates the month.**

  | `flow_basis` | Means | `*_value_thousands` |
  |---|---|---|
  | `delta` | A real one-session difference between two consecutive snapshots | A flow |
  | `month_open` | The month's first session, where the month-to-date total *is* the day | A flow |
  | `unknown_opening_snapshot` | No earlier snapshot is held for that month | **`null`, by construction** |

  `null` here means *we do not know what happened on this day* — not zero flow, not a quiet session. A `sum()` skips nulls silently and hands you a month total missing an unknown number of days, which looks exactly like a real, smaller number.

  Either restrict to `flow_basis=in.(delta,month_open)` and know your window is partial, or keep every row and treat the nulls as gaps. Do not aggregate across all three without looking.
</Warning>

| Column | Type | Meaning |
| --- | --- | --- |
| `reference_date` | date | The session the flow is for. Part of the grain. |
| `investor_type` | text | Investor class as published. Part of the grain. |
| `flow_basis` | text | `delta` \| `month_open` \| `unknown_opening_snapshot`. **Read this first.** |
| `buy_value_thousands` | numeric | The session's purchases, in R$ thousands. Null on `unknown_opening_snapshot`. |
| `sell_value_thousands` | numeric | The session's sales. Null on the same rows. |
| `net_value_thousands` | numeric | `buy - sell`. Positive is net buying. Null on the same rows. |
| `mtd_buy_value_thousands` | numeric | B3's **cumulative** month-to-date purchases as published — the figure the difference was taken from. Never null. |
| `mtd_sell_value_thousands` | numeric | Cumulative month-to-date sales as published. |

**Note**: units are R$ thousands, from the source's own `brl_mil` fields. Multiply by 1,000 for reais; do not assume millions.

The `mtd_*` columns are the audit: within a month, `mtd_buy_value_thousands` on consecutive sessions should differ by exactly `buy_value_thousands` on the later one. They are published beside the differenced values so you can check the arithmetic rather than trust it.

### Example

One investor type across a month, with the uninterpretable rows kept visible:

<CodeGroup>

```bash curl
curl -s -G "$SILO_URL/investor_flow" \
  -H "apikey: $SILO_ANON_KEY" \
  --data-urlencode "select=reference_date,investor_type,flow_basis,net_value_thousands,mtd_buy_value_thousands" \
  --data-urlencode "investor_type=eq.Investidor Estrangeiro" \
  --data-urlencode "reference_date=gte.2026-09-01" \
  --data-urlencode "order=reference_date.asc"
```

params = {

### What this is not

- **Not a flow by security.** The grain is investor *type*, market-wide. No per-ticker breakdown exists in the source, so aligning it against one ticker's return is your inference to own.
- **Not a position.** Gross purchases and sales over a session. A net figure is the session's direction, not anyone's holdings.
- **Not a panel metric.** These rows carry no id in the panel's sense, so there is no [`panel`](/api-docs/panel) arm — the same reason [`anbima_classes`](/api-docs/anbima) has none.

### Paging and empty results

The 1,000-row page **cuts silently with a `200`** on a view, keeping the oldest rows. Send `Prefer: count=exact` and read `Content-Range`, or page with `limit`/`offset` and an explicit `order`. The [SDK](/api-docs/sdk) does both: `silo.investor_flow(...)` for one page, `silo.view_all("investor_flow", order="reference_date.asc")` to walk them all.

A whole capture window fits inside one page today — a property of the ratchet, not a guarantee.

- **Unknown investor type → `200 []`.** Spelling must match B3's.
- **Empty window → `200 []`.** Common, given the retention and the T+2 lag. Check [`coverage`](/api-docs/coverage) first.
- The landing tables are not readable by client roles.
