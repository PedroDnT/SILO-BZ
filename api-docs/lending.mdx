### Overview

Four views over B3's securities-lending market — what is on loan, at what rate, and who traded it. Together they are the closest thing the Brazilian market publishes to a short interest report.

| Endpoint | Grain | What it holds |
|---|---|---|
| `GET /short_interest` | `(ticker, trade_date)` | Balance on loan, % of float with the basis that produced it, days to cover, lending rates |
| `GET /short_interest_by_sector` | `(sector, trade_date)` | The same book aggregated by B3 top-level sector |
| `GET /lending_trades` | `(ticker, trade_date)` | The session's trade tape per ticker: count, quantity, quantity-weighted rate |
| `GET /lending_participants` | `(ticker, trade_date, broker_code)` | What each **brokerage** lent and borrowed |

These are **views**, not RPCs: `GET`, PostgREST filters (`?ticker=eq.PETR4`), `limit`/`offset` paging. Investor-type flow is on [Investor flow](/api-docs/flows).

<Warning>
  **History starts when SILO started capturing, and can never be extended backwards.** B3 keeps roughly **21 business days** of these tables and publishes no archive — no paid tier, no vendor feed, no request that returns an earlier session.

  - **A short window is the source's retention, not a data problem.** Do not read the first date as a market event or a bug.
  - **You cannot compute a long-run average, a 52-week range, or a year-over-year change** until SILO has held them that long.
</Warning>

### `GET /short_interest`

Short interest per `(ticker, trade_date)`, built from B3's own `Total` rows so balances are never double-counted.

PostgREST filters on any returned column. The ones worth knowing:

| Param | Meaning |
| --- | --- |
| `ticker` | `eq.PETR4`. |
| `trade_date` | `eq.2026-09-16`, or `gte.` / `lte.`. Sessions only — no weekend rows. |
| `float_basis` | `eq.index_free_float` or `eq.shares_outstanding`. **Required for any ranking.** |
| `instrument_category` | `eq.SHARES`, `eq.UNIT`, `eq.ETF EQUITIES`, `eq.BDR`, `eq.FUNDS`. |
| `select` / `order` / `limit` | Column list, sort, page size (capped at 1,000). |

An unfiltered days-to-cover screen is dominated by index ETFs, which are legitimately on loan against small secondary volume but are not the crowded single-name shorts the screen is for.

#### `pct_float` is two different metrics

<Warning>
  **Reading `pct_float` without `float_basis` is the easiest way to produce a confident, wrong ranking.**

  | `float_basis` | Denominator | Coverage | Reads |
  |---|---|---|---|
  | `index_free_float` | B3's published free float (`theoretical_qty`) from the broadest index portfolio carrying the ticker | Index constituents only, ~149 tickers | The free-float percentage the market quotes |
  | `shares_outstanding` | Capital social from the cash instrument registry | Everything else with a registry entry | A **smaller** percentage for the same position |

  They are never comparable. **Any ranking must filter to one basis first**, or it sorts index members against non-members on an axis they do not share — and because the free-float basis produces systematically larger percentages, an unfiltered "most shorted" list is really a list of index constituents.

  `float_denominator` carries the number used. The index priority is IBRA → SMLL → IBXX → IBOV: index weight caps can only shrink the quantity below the real float, so the broadest index is the closest published estimate.
</Warning>

**Note**: `pct_float` and `days_to_cover` are `null`, never `0`, when their denominator is missing. A short position in a name that has not traded is *uncoverable*, not instantly coverable, and a `0` would sort it to the wrong end of a screen. Filter nulls out deliberately.

| Column | Type | Meaning |
| --- | --- | --- |
| `trade_date` | date | Session date. Part of the grain. |
| `ticker` | text | B3 negotiation code. Part of the grain. |
| `asset_name` | text | From the registry where available, else B3's `empresa`. |
| `isin` | text | ISIN as published. |
| `sector` | text | B3's full `Setor / Subsetor` string, ~34 buckets. |
| `sector_top` | text | The part before the slash, with B3's spelling variants merged. No ticker is moved between sectors; an unrecognised prefix passes through verbatim. Null outside the index universe. |
| `instrument_category` | text | `SHARES`, `UNIT`, `BDR`, `ETF EQUITIES`, `FUNDS`. |
| `short_quantity` | numeric | Shares on loan, summed across specifications (a ticker can carry `ON` and `ON NM`). |
| `short_value` | numeric | Balance on loan in BRL. |
| `pct_float` | numeric | `short_quantity` over `float_denominator`, in percentage points. **Read with `float_basis`.** |
| `float_basis` | text | `index_free_float` \| `shares_outstanding` \| `null`. |
| `float_denominator` | numeric | The share count actually divided by. |
| `days_to_cover` | numeric | `short_quantity / adtv_qty_21` — sessions of average volume to buy the position back. Null when the name did not trade. |
| `adtv_value_21` | numeric | Trailing 21-session average traded value in BRL, computed per short-interest date. |
| `adtv_sessions` | integer | How many sessions that average covers. Fewer than 21 means a shorter, noisier window. |
| `lender_rate_pct` | numeric | Quantity-weighted rate paid to the lender, pp a.a. Markets with no registered quantity are excluded. |
| `borrower_rate_pct` | numeric | Quantity-weighted rate charged to the borrower, pp a.a. |
| `contracts` | numeric | Registered contracts for the session. |

#### Example

The most heavily shorted index names in a session. Without the `float_basis` filter this ranking is meaningless:

<CodeGroup>

```bash curl
curl -s -G "$SILO_URL/short_interest" \
  -H "apikey: $SILO_ANON_KEY" \
  --data-urlencode "select=ticker,trade_date,pct_float,float_basis,days_to_cover,short_value" \
  --data-urlencode "trade_date=eq.2026-09-16" \
  --data-urlencode "float_basis=eq.index_free_float" \
  --data-urlencode "instrument_category=eq.SHARES" \
  --data-urlencode "order=pct_float.desc" \
  --data-urlencode "limit=25"
```

```python Python
params = {
    "select": "ticker,trade_date,pct_float,float_basis,days_to_cover,short_value",
    "trade_date": "eq.2026-09-16",
    # Not optional: the two bases are different denominators.
    "float_basis": "eq.index_free_float",
    "instrument_category": "eq.SHARES",
    "order": "pct_float.desc",
    "limit": 25,
}
rows = requests.get(f"{URL}/short_interest", headers=H, params=params).json()
```

```javascript JavaScript
const { data } = await supabase
  .from('short_interest')
  .select('ticker,trade_date,pct_float,float_basis,days_to_cover,short_value')
  .eq('trade_date', '2026-09-16')
  .eq('float_basis', 'index_free_float')
  .eq('instrument_category', 'SHARES')
  .order('pct_float', { ascending: false })
  .limit(25)
```

</CodeGroup>

### `GET /short_interest_by_sector`

The same book aggregated by B3 top-level sector, one row per `(sector, trade_date)`. Filters: `trade_date`, `sector`, plus `select` / `order` / `limit`.

| Column | Type | Meaning |
| --- | --- | --- |
| `trade_date` | date | Session date. |
| `sector` | text | B3 top-level sector, or `Não classificado`. |
| `tickers` | integer | How many tickers went into the bucket. |
| `short_value` | numeric | Total balance on loan for the sector, BRL. |
| `short_value_equities` | numeric | The same total restricted to `SHARES` and `UNIT`. |
| `short_quantity` | numeric | Total shares on loan. |

**Note**: `Não classificado` is a real bucket, not a rounding bin. Sector comes from the B3 index portfolios, so ETFs, BDRs and every off-index name land there — bucketed rather than dropped, because a sector chart that omits a third of the book is worse than one that shows the gap. For single-name risk read `short_value_equities`.

### `GET /lending_trades`

The session's individual lending trades, aggregated per `(ticker, trade_date)`. Filters: `ticker`, `trade_date`, plus `select` / `order` / `limit`.

| Column | Type | Meaning |
| --- | --- | --- |
| `trade_date` / `ticker` | date / text | The grain. |
| `trades` | integer | Number of trades in the session. |
| `quantity` | numeric | Total shares traded. |
| `rate_pct` | numeric | **Quantity-weighted** average annualized rate, pp. |
| `rate_min_pct` / `rate_max_pct` | numeric | Lowest and highest rate printed. |
| `borrower_brokers` / `lender_brokers` | integer | Distinct **brokerages** on each leg — not distinct borrowers or lenders. |
| `internal_trades` | integer | Trades where the same broker code stood on both legs. Usually most of them. |

**Note**: `rate_pct` and B3's own published average are both right, and they differ — this view weights by **quantity**, B3's glossary weights by **number of trades**. Measured 2026-09-10 across the 569 tickers both cover: mean absolute difference 0.037pp, 561 of 569 within 0.5pp, largest gap 3.81pp. The residual is method, not error.

### `GET /lending_participants`

One row per `(ticker, trade_date, broker_code)`: what each brokerage lent and borrowed. Filters: `ticker`, `trade_date`, `broker_code`, plus `select` / `order` / `limit`.

<Warning>
  **`doador` and `tomador` are BROKERAGES, not beneficial owners.** B3 names about 33 participants in a whole session, and on 2026-09-10 **32,197 of 43,165 trades (74.6%)** carried the same code on both legs — a broker crossing its own client book. A large `quantity_borrowed` is that broker's *clients'* position. "The biggest short in the market" read off this view is a statement about order routing.

  **`internal_legs` and `internal_qty` tell the two apart.** A high internal share is client churn; a low one is flow that crossed the market. In that session J.P. Morgan sat at ~6% internal — directional flow — while Morgan Stanley was at ~78%. Same tape, opposite readings.
</Warning>

| Column | Type | Meaning |
| --- | --- | --- |
| `trade_date` / `ticker` | date / text | Part of the grain. |
| `broker_code` | text | B3 participant code. Part of the grain. **The intermediary, never the owner.** |
| `broker_name` | text | Participant name as published. |
| `quantity_lent` / `quantity_borrowed` | numeric | Shares this broker lent / borrowed in the session. |
| `quantity_net` | numeric | `lent - borrowed`. An internally crossed trade contributes to **both** sides, so it cancels here rather than inflating either direction. |
| `lender_rate_pct` / `borrower_rate_pct` | numeric | Quantity-weighted rate on each leg, pp a.a. |
| `internal_legs` | integer | Legs where this broker was on both sides. |
| `internal_qty` | numeric | Quantity on those legs. Compare against `quantity_lent + quantity_borrowed` for the internal share. |

<CodeGroup>

```bash curl
curl -s -G "$SILO_URL/lending_participants" \
  -H "apikey: $SILO_ANON_KEY" \
  --data-urlencode "ticker=eq.PETR4" \
  --data-urlencode "trade_date=eq.2026-09-16" \
  --data-urlencode "order=quantity_borrowed.desc" \
  --data-urlencode "limit=10"
```

```python Python
params = {
    "ticker": "eq.PETR4",
    "trade_date": "eq.2026-09-16",
    "order": "quantity_borrowed.desc",
    "limit": 10,
}
rows = requests.get(f"{URL}/lending_participants", headers=H, params=params).json()

# Separates a directional borrow from a broker's own client churn.
for r in rows:
    gross = (r["quantity_lent"] or 0) + (r["quantity_borrowed"] or 0)
    internal_share = (r["internal_qty"] or 0) / gross if gross else None
    print(r["broker_name"], r["quantity_borrowed"], internal_share)
```

```javascript JavaScript
const { data } = await supabase
  .from('lending_participants')
  .select('*')
  .eq('ticker', 'PETR4')
  .eq('trade_date', '2026-09-16')
  .order('quantity_borrowed', { ascending: false })
  .limit(10)
```

</CodeGroup>

### Paging and empty results

These are views, so the 1,000-row page **cuts silently with a `200`**, keeping the oldest rows — it does not raise the way RPC functions do.

- Send `Prefer: count=exact` and read `Content-Range`. `0-999/*` means the response was cut; `0-999/4382` gives the true total.
- Page with `limit` / `offset` and an explicit `order`. Offset paging without a total order can duplicate one row and drop another at a page boundary.
- The [SDK](/api-docs/sdk) wraps both: `silo.short_interest(...)` raises `SiloTruncated` on an unbounded cut, `silo.view_all("short_interest", order="trade_date.desc")` walks every page.
- A whole session of `lending_participants` is over one page — filter by `ticker` or page it.

Unknown ticker, or a known ticker with no rows in the window → `200 []`, never a fabricated balance. With ~21 business days of retention the empty window is the common case — check [`coverage`](/api-docs/coverage) first. The landing tables are not readable by client roles.
