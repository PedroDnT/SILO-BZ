Four views over B3's securities-lending market — what is on loan, at what rate, and who
traded it. Together they are the closest thing the Brazilian market publishes to a short
interest report.

| Endpoint | Grain | What it holds |
|---|---|---|
| `GET /short_interest` | `(ticker, trade_date)` | Balance on loan, % of float with the basis that produced it, days to cover, lending rates |
| `GET /short_interest_by_sector` | `(sector, trade_date)` | The same book aggregated by B3 top-level sector |
| `GET /lending_trades` | `(ticker, trade_date)` | The session's trade tape per ticker: count, quantity, quantity-weighted rate |
| `GET /lending_participants` | `(ticker, trade_date, broker_code)` | What each **brokerage** lent and borrowed |

These are **views**, not RPCs: read them with `GET`, filter them with PostgREST syntax
(`?ticker=eq.PETR4`), and page them with `limit`/`offset`. Investor-type flow lives on its
own page, [Investor flow](/api-docs/flows).

<Warning>
  **History starts when SILO started capturing, and it can never be extended backwards.**

  B3 keeps roughly **21 business days** of these tables and publishes no archive. There is
  no paid tier, no vendor feed and no request that returns an earlier session — a day
  nobody captured is gone. This is the only part of this warehouse that behaves this way;
  everywhere else a gap is a backfill waiting to be run.

  Two consequences worth stating plainly:

  - **A short window is the source's retention, not a data problem.** Do not read the
    first date in these views as a market event, a listing date, or a bug. Call
    [`coverage`](/api-docs/coverage) and read `as_of` together with the ratchet note it
    carries on every one of these rows.
  - **You cannot compute a long-run average, a 52-week range, or a year-over-year change**
    from these endpoints until SILO has held them that long. A ratio against a "historical
    norm" that only has three weeks behind it is a number about the capture window, not
    about the market.

  An over-wide request to B3 returns HTTP 200 with a silently clamped window, which is why
  the ingest reconciles the sessions it asked for against the ones it received.
</Warning>

## `GET /short_interest`

Short interest per `(ticker, trade_date)`, built from B3's own `Total` rows so balances are
never double-counted.

### Parameters

PostgREST filters on any returned column. The ones worth knowing:

<ParamField query="ticker" type="string">
  `eq.PETR4`. The B3 negotiation code.
</ParamField>

<ParamField query="trade_date" type="date">
  `eq.2026-09-16`, or `gte.` / `lte.` for a window. Sessions only — B3 publishes no
  weekend rows.
</ParamField>

<ParamField query="float_basis" type="string">
  `eq.index_free_float` or `eq.shares_outstanding`. **Required for any ranking** — see
  below.
</ParamField>

<ParamField query="instrument_category" type="string">
  `eq.SHARES`, `eq.UNIT`, `eq.ETF EQUITIES`, `eq.BDR`, `eq.FUNDS`. An unfiltered
  days-to-cover screen is dominated by index ETFs, which are legitimately on loan against
  small secondary volume but are not the crowded single-name shorts the screen is for.
</ParamField>

<ParamField query="select" type="string">
  Column list, e.g. `ticker,trade_date,pct_float,float_basis`.
</ParamField>

<ParamField query="order" type="string">
  e.g. `pct_float.desc`. Nulls sort last by default in PostgREST; add `.nullslast`
  explicitly if you rely on it.
</ParamField>

<ParamField query="limit" type="integer">
  Page size, capped at 1,000 server-side. Pair with `offset` to page.
</ParamField>

### `pct_float` is two different metrics

<Warning>
  **`pct_float` is not one number, and `float_basis` is the column that says which one you
  are holding.** Reading it without the basis is the single easiest way to produce a
  confident, wrong ranking.

  | `float_basis` | Denominator | Coverage | Reads |
  |---|---|---|---|
  | `index_free_float` | B3's published free float (`theoretical_qty`) from the broadest index portfolio carrying the ticker | Index constituents only, ~149 tickers | The free-float percentage the market quotes |
  | `shares_outstanding` | Capital social from the cash instrument registry | Everything else with a registry entry | A **smaller** percentage for the same position — the denominator is larger |

  They are not the same measure, and they are never comparable. **Any ranking, screen or
  cross-section on `pct_float` must filter to one basis first**, or it sorts index members
  against non-members on an axis they do not share — and because the free-float basis
  produces systematically larger percentages, an unfiltered "most shorted" list is really a
  list of index constituents.

  `float_denominator` carries the number actually used, and `float_source_index` (on the
  underlying `dim_ticker_float`) records which portfolio it came from. The index priority
  is IBRA → SMLL → IBXX → IBOV, because index weight caps can only shrink the quantity
  below the real float, so the broadest index is the closest published estimate.
</Warning>

<Note>
  **`pct_float` and `days_to_cover` are `null`, never `0`, when their denominator is
  missing.** An unknown float is unknown; `0%` would read as "nobody is short". A short
  position in a name that has not traded is *uncoverable*, not instantly coverable, and a
  `0` would sort it to exactly the wrong end of a screen. Filter nulls out deliberately —
  do not let them fall to the bottom by accident.
</Note>

### Returns

<ResponseField name="trade_date" type="date">
  Session date. Part of the grain.
</ResponseField>
<ResponseField name="ticker" type="text">
  B3 negotiation code. Part of the grain.
</ResponseField>
<ResponseField name="asset_name" type="text">
  Instrument name, from the registry where available, else B3's `empresa` field.
</ResponseField>
<ResponseField name="isin" type="text">
  ISIN as published.
</ResponseField>
<ResponseField name="sector" type="text">
  B3's full `Setor / Subsetor` string, ~34 buckets.
</ResponseField>
<ResponseField name="sector_top" type="text">
  The part before the slash — B3's own top-level sector, with the source's spelling
  variants merged (`Bens Indls` and `Bens Industriais` are one sector). No ticker is moved
  between sectors and no taxonomy is invented; a prefix the merge list does not recognise
  passes through verbatim. `null` outside the index universe.
</ResponseField>
<ResponseField name="instrument_category" type="text">
  `SHARES`, `UNIT`, `BDR`, `ETF EQUITIES`, `FUNDS` — from the instrument registry.
</ResponseField>
<ResponseField name="short_quantity" type="numeric">
  Shares on loan, summed across specifications (a ticker can carry `ON` and `ON NM`).
</ResponseField>
<ResponseField name="short_value" type="numeric">
  Balance on loan in **BRL**.
</ResponseField>
<ResponseField name="pct_float" type="numeric">
  `short_quantity` as a percentage of `float_denominator`, in **percentage points**.
  **Read with `float_basis`.** `null` when there is no denominator.
</ResponseField>
<ResponseField name="float_basis" type="text">
  `index_free_float` | `shares_outstanding` | `null`. Which denominator produced
  `pct_float`.
</ResponseField>
<ResponseField name="float_denominator" type="numeric">
  The share count actually divided by.
</ResponseField>
<ResponseField name="days_to_cover" type="numeric">
  Short interest ratio: sessions of average volume needed to buy the position back
  (`short_quantity / adtv_qty_21`). `null` when the name did not trade.
</ResponseField>
<ResponseField name="adtv_value_21" type="numeric">
  Trailing 21-session average traded value in BRL, computed per short-interest date — a
  row dated three weeks ago is divided by the volume that actually preceded *it*.
</ResponseField>
<ResponseField name="adtv_sessions" type="integer">
  How many sessions that average actually covers. Fewer than 21 (early in a listing, or
  after a halt) means a shorter, noisier window — a usable estimate, but you are told
  rather than left to assume.
</ResponseField>
<ResponseField name="lender_rate_pct" type="numeric">
  Quantity-weighted average rate paid to the lender, **percentage points a.a.** Markets
  with no registered quantity are excluded so a nominal rate on zero business cannot drag
  the average.
</ResponseField>
<ResponseField name="borrower_rate_pct" type="numeric">
  Quantity-weighted average rate charged to the borrower, percentage points a.a.
</ResponseField>
<ResponseField name="contracts" type="numeric">
  Number of registered contracts for the session.
</ResponseField>

### Example

The most heavily shorted index names in a session. Note the `float_basis` filter — without
it this ranking is meaningless:

<CodeGroup>

```bash curl
curl -s -G "$SILO_URL/short_interest" \
  -H "apikey: $SILO_ANON_KEY" \
  --data-urlencode "select=ticker,trade_date,pct_float,float_basis,days_to_cover,short_value" \
  --data-urlencode "trade_date=eq.2026-09-16" \
  --data-urlencode "float_basis=eq.index_free_float" \
  --data-urlencode "instrument_category=eq.SHARES" \
  --data-urlencode "order=pct_float.desc" \
  --data-urlencode "limit=25"
```

```python Python
params = {
    "select": "ticker,trade_date,pct_float,float_basis,days_to_cover,short_value",
    "trade_date": "eq.2026-09-16",
    # Not optional: index_free_float and shares_outstanding are different
    # denominators, and ranking across both compares nothing.
    "float_basis": "eq.index_free_float",
    "instrument_category": "eq.SHARES",
    "order": "pct_float.desc",
    "limit": 25,
}
rows = requests.get(f"{URL}/short_interest", headers=H, params=params).json()
```

```javascript JavaScript
const { data } = await supabase
  .from('short_interest')
  .select('ticker,trade_date,pct_float,float_basis,days_to_cover,short_value')
  .eq('trade_date', '2026-09-16')
  .eq('float_basis', 'index_free_float')
  .eq('instrument_category', 'SHARES')
  .order('pct_float', { ascending: false })
  .limit(25)
```

</CodeGroup>

## `GET /short_interest_by_sector`

The same book aggregated by B3 top-level sector, one row per `(sector, trade_date)`.

### Parameters

`trade_date` and `sector` filters, plus the usual `select` / `order` / `limit`.

### Returns

<ResponseField name="trade_date" type="date">
  Session date.
</ResponseField>
<ResponseField name="sector" type="text">
  B3 top-level sector, or **`Não classificado`**.
</ResponseField>
<ResponseField name="tickers" type="integer">
  How many tickers went into the bucket.
</ResponseField>
<ResponseField name="short_value" type="numeric">
  Total balance on loan for the sector, BRL.
</ResponseField>
<ResponseField name="short_value_equities" type="numeric">
  The same total restricted to `SHARES` and `UNIT`.
</ResponseField>
<ResponseField name="short_quantity" type="numeric">
  Total shares on loan for the sector.
</ResponseField>

<Note>
  **`Não classificado` is a real bucket, not a rounding bin.** Sector comes from the B3
  index portfolios, which cover the index universe and nothing else — so ETFs, BDRs and
  every off-index name land there. They are bucketed rather than dropped, because a sector
  chart that quietly omits a third of the short book is worse than one that shows the gap.
  If you want single-name risk, read `short_value_equities`, which restricts to `SHARES`
  and `UNIT`; the unclassified bucket is almost entirely ETFs and BDRs and would otherwise
  dominate the bar.
</Note>

## `GET /lending_trades`

The session's individual lending trades, aggregated per `(ticker, trade_date)`.

### Parameters

`ticker`, `trade_date`, plus `select` / `order` / `limit`.

### Returns

<ResponseField name="trade_date" type="date">
  Session date. Part of the grain.
</ResponseField>
<ResponseField name="ticker" type="text">
  B3 negotiation code. Part of the grain.
</ResponseField>
<ResponseField name="trades" type="integer">
  Number of trades in the session.
</ResponseField>
<ResponseField name="quantity" type="numeric">
  Total shares traded.
</ResponseField>
<ResponseField name="rate_pct" type="numeric">
  **Quantity-weighted** average annualized rate, percentage points.
</ResponseField>
<ResponseField name="rate_min_pct" type="numeric">
  Lowest rate printed in the session.
</ResponseField>
<ResponseField name="rate_max_pct" type="numeric">
  Highest rate printed in the session.
</ResponseField>
<ResponseField name="borrower_brokers" type="integer">
  Distinct **brokerages** on the borrowing leg — not distinct borrowers.
</ResponseField>
<ResponseField name="lender_brokers" type="integer">
  Distinct brokerages on the lending leg.
</ResponseField>
<ResponseField name="internal_trades" type="integer">
  Trades where the same broker code stood on both legs. See below — this is usually most
  of them.
</ResponseField>

<Note>
  **`rate_pct` and B3's own published average are both right, and they differ.** This view
  weights by **quantity**; B3's glossary defines its published average as weighted by the
  **number of trades**. They diverge exactly where one broker does many small trades at a
  rate far from the size-weighted middle.

  Measured 2026-09-10 across the 569 tickers both cover: mean absolute difference **0.037
  percentage points**, 561 of 569 within 0.5pp, largest gap 3.81pp. The residual is method,
  not error. This view does not overwrite B3's figure — keeping both is what lets you check
  one against the other.
</Note>

## `GET /lending_participants`

One row per `(ticker, trade_date, broker_code)`: what each brokerage lent and borrowed.

<Warning>
  **`doador` and `tomador` are BROKERAGES. They are not beneficial owners, and reading them
  as owners will produce a confident, wrong story about who is short.**

  B3 names about **33 participants** in a whole session, and on 2026-09-10 **32,197 of
  43,165 trades (74.6%)** carried the **same code on both legs** — a broker crossing its
  own client book. So a large `quantity_borrowed` through a broker is that broker's
  *clients'* position, not a view the broker took. "The biggest short in the market" read
  off this view is a statement about order routing.

  **`internal_legs` and `internal_qty` are what tell the two apart.** A high internal share
  is client churn; a low one is flow that actually crossed the market. In the source
  session, J.P. Morgan sat at ~6% internal — directional flow — while Morgan Stanley was at
  ~78%, which is client churn. Same tape, opposite readings.

  They sit beside the totals rather than being netted away on purpose: dropping the
  self-crossed trades makes the remainder look like inter-broker conviction, and keeping
  them silently makes internal churn look like directional demand. Both are misreadings, so
  the split is published and the choice is yours.
</Warning>

### Parameters

`ticker`, `trade_date`, `broker_code`, plus `select` / `order` / `limit`.

### Returns

<ResponseField name="trade_date" type="date">
  Session date. Part of the grain.
</ResponseField>
<ResponseField name="ticker" type="text">
  B3 negotiation code. Part of the grain.
</ResponseField>
<ResponseField name="broker_code" type="text">
  B3 participant code. Part of the grain. **The intermediary, never the owner.**
</ResponseField>
<ResponseField name="broker_name" type="text">
  Participant name as B3 publishes it.
</ResponseField>
<ResponseField name="quantity_lent" type="numeric">
  Shares this broker lent in the session.
</ResponseField>
<ResponseField name="quantity_borrowed" type="numeric">
  Shares this broker borrowed.
</ResponseField>
<ResponseField name="quantity_net" type="numeric">
  `quantity_lent - quantity_borrowed`. Positive means the broker's book lent more than it
  borrowed. A trade crossed internally contributes to **both** sides, so it cancels here
  rather than inflating either direction.
</ResponseField>
<ResponseField name="lender_rate_pct" type="numeric">
  Quantity-weighted rate on the lending leg, percentage points a.a.
</ResponseField>
<ResponseField name="borrower_rate_pct" type="numeric">
  Quantity-weighted rate on the borrowing leg.
</ResponseField>
<ResponseField name="internal_legs" type="integer">
  Legs where this broker was on both sides of the trade.
</ResponseField>
<ResponseField name="internal_qty" type="numeric">
  Quantity on those internal legs. Compare against
  `quantity_lent + quantity_borrowed` to get the internal share.
</ResponseField>

### Example

Who was borrowing one ticker, and how much of it was real:

<CodeGroup>

```bash curl
curl -s -G "$SILO_URL/lending_participants" \
  -H "apikey: $SILO_ANON_KEY" \
  --data-urlencode "ticker=eq.PETR4" \
  --data-urlencode "trade_date=eq.2026-09-16" \
  --data-urlencode "order=quantity_borrowed.desc" \
  --data-urlencode "limit=10"
```

```python Python
params = {
    "ticker": "eq.PETR4",
    "trade_date": "eq.2026-09-16",
    "order": "quantity_borrowed.desc",
    "limit": 10,
}
rows = requests.get(f"{URL}/lending_participants", headers=H, params=params).json()

# The column that separates a directional borrow from a broker's own client churn.
for r in rows:
    gross = (r["quantity_lent"] or 0) + (r["quantity_borrowed"] or 0)
    internal_share = (r["internal_qty"] or 0) / gross if gross else None
    print(r["broker_name"], r["quantity_borrowed"], internal_share)
```

```javascript JavaScript
const { data } = await supabase
  .from('lending_participants')
  .select('*')
  .eq('ticker', 'PETR4')
  .eq('trade_date', '2026-09-16')
  .order('quantity_borrowed', { ascending: false })
  .limit(10)
```

</CodeGroup>

## Row caps and paging

These are views, so the 1,000-row page is PostgREST's `db-max-rows` and it **cuts silently
with a 200**, keeping the oldest rows — it does not raise the way the RPC functions do. Two
ways to stay honest about it:

- Send `Prefer: count=exact` and read the `Content-Range` response header. `0-999/*` means
  the response was cut; `0-999/4382` tells you the true total.
- Page with `limit` / `offset` and an explicit `order`. Offset paging without a total order
  can duplicate one row and drop another at a page boundary with nothing to say so.

The [Python SDK](/api-docs/sdk) wraps both: `silo.short_interest(...)` returns one page and
raises `SiloTruncated` on an unbounded cut, and `silo.view_all("short_interest",
order="trade_date.desc")` walks every page.

A whole session of `lending_participants` is comfortably over one page — it is one row per
`(ticker, broker)` — so filter by `ticker` or page it.

## Empty and error behavior

- **Unknown ticker → `200 []`.** Never a fabricated balance.
- **Known ticker, no rows in the window → `200 []`.** With a ~21-business-day retention
  this is the common case, not the exceptional one. Check
  [`coverage`](/api-docs/coverage)'s `short_interest` / `lending_trades` rows before
  concluding anything from an empty result.
- The landing tables (`b3_lending_open_position`, `b3_lending_rate`, `b3_lending_trade`)
  are **not** readable by client roles. These views are owner-privileged, so the columns
  they select are the whole boundary.
