### 2. What we could ingest and don't

Everything here is published and reachable. Each line is a decision, not an oversight. The measurements behind them are in the [repository inventory](https://github.com/PedroDnT/SILO-BZ/blob/main/docs/DATA_INVENTORY.md) §2.

#### CVM CDA — the unread blocks

The monthly CDA archive holds eight blocks; we read four. Adding one costs a field map, a migration and one `ingest_*` method — the download already happens.

| Block | Content                  | Status                                                                  |
| ----- | ------------------------ | ------------------------------------------------------------------------- |
| BLC_1 | Títulos públicos         | **ingested** (`cvm_fi_cda`)                                              |
| BLC_2 | Cotas de fundos          | **ingested** (`cvm_fi_cda_cotas`)                                        |
| BLC_4 | Ações / BDR              | **ingested** (`cvm_fi_cda_acoes`)                                        |
| BLC_6 | Debêntures               | **ingested** (`cvm_fi_cda_debentures`) — no `CD_ATIVO`, so the key ends in `row_hash` |
| BLC_3 | Swaps                    | not ingested — no consumer asked                                         |
| BLC_5 | Títulos privados         | not ingested                                                             |
| BLC_7 | Investimento no exterior | not ingested                                                             |
| BLC_8 | Disponibilidades         | not ingested — 28.9% of the archive by size for cash balances            |

#### FIDC informe mensal — the tabs still unread

Ten of the ZIP's 18 members are ingested. Still unread: tab I's other ~70 columns (asset composition, admin, condomínio), `III` (2025+), `V` (maturity ladder), `VII` (custody split, repurchases), `IX` (assignment prices), `X_1` / `X_1_1` (quotaholders per tranche and by investor type), `X_5` (liquidity ladder), `X_7` (collateral coverage).

#### B3 — possible additions

These require source and access checks before they become implementation work.
`b3_index_portfolio` already captures B3's current constituent portfolio and
feeds short-interest analytics; a historical effective-vintage series would be
a distinct addition, subject to archive and layout verification.

| Source | What it could give | Gate before adding |
| --- | --- | --- |
| Futures settlement (DI1) | Daily settlement per contract | Verify a maintainable public file and its historical coverage |
| Reference-rate curves (PRE) | A published yield curve | Confirm no-cost access, terms and history |
| Historical index composition | Point-in-time membership and weights beyond the current portfolio SILO captures | Verify the archive, effective dates and each CIND layout version |

#### Known defects in what is ingested

Two, both written up in full with their measurements in the repository inventory:

- **`cvm_fi_cda` keeps one bond in five and calls it the class total.** BLC_1 is one row per security, but the shipped key carries none of `CD_SELIC` / `CD_ISIN` / `DT_VENC`, so 80.4% of rows are lost on upsert — the stored number is one arbitrary bond's position wearing the label of the fund's whole government-bond book. The fix is additive: a `cvm_fi_cda_titpub` table keyed on the security, leaving `cvm_fi_cda` as the class roll-up the dashboards read.
- **`cia_event` cannot key an IPE filing with no protocol, and before 2015 none have one.** The natural key is `(protocolo, versao)`, so those rows are dropped rather than given a synthesized key. 2010–2014 cannot be loaded at all; 2015 silently loses 12% of its filings. The fix is a second key era (a `row_hash` for protocol-less rows), which changes the grain and so waits for the owner's call.

#### Periods no wired source reaches

| Gap                                      | Why                                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| FIDC tranche / flows / aging before 2025 | CVM publishes **no HIST equivalent** for tabs X2/X4/VI — an upstream limit, not a backlog item. |
| FIAGRO before 2025-05                    | the monthly file itself begins there                                                            |
| CIA ITR/DFP 2010–2018                    | pipeline is wired from 2019; partitions are declared and empty                                  |
| `cvm_fi_diario` before 2019              | RANGE partitions floor at 2019-01-01. Adding CVM's HIST back to 2000 means ~a decade of daily rows on the largest table. Deliberate. |

#### Not ingested by decision

- **Company ↔ fund ownership beyond CDA.** Two published edges exist and neither is inferred: `cvm_fi_cda_acoes.cd_ativo` (the B3 ticker, joined to `cia_ticker`) and `cvm_fi_cda_debentures.cpf_cnpj_emissor` (which joins to `cia_*` directly). No name matching, ever.
- **Anything requiring a licence or a login.** `etf_market_snapshot` is the one scrape, and it self-skips without its token.

### 4. How it is served

Five objects do the work. Everything else is a typed view over `b3_cotahist`.

```
coverage()  →  what is here, and how complete   (read this FIRST)
lookup()    →  a name/ISIN/CNPJ/ticker → an id you can query
panel()     →  (id, date, metric, value) — mix tickers and fund CNPJs
quote_*()   →  one instrument's own series
fund_*()    →  one fund's own series
```

`panel` is the primitive. Correlation, ranking and spreads are reductions of a panel and happen in the client.

#### Grain, family by family

| Family  | Native grain                         | Served as                    | Consequence                                                                     |
| ------- | ------------------------------------ | ---------------------------- | --------------------------------------------------------------------------------- |
| B3 cash | **session**                          | day, or month = last session | a monthly close is a real print, never an average                                |
| FI      | fund × day (`cvm_fi_diario`)         | **month**                    | the daily rows exist but the panel does not serve them for funds                 |
| FIDC    | fund × month-end                     | month                        | `delinquency` is a **BRL value**, not a rate — divide by `nav` yourself          |
| FII     | fund × month                         | month                        | the only family carrying `yield`                                                 |
| FIAGRO  | fund × month                         | month                        | begins 2025-05; a shorter axis, not a thinner one                                |
| FIP     | fund × **filing date** × share class | month                        | files 3–4× a year, not annually                                                  |
| CIA     | company × filing × account line      | **not served** by `panel`    | the grain is a statement line, which no fund-shaped endpoint fits                |

**FIP is the one to know about.** It reads as annual and is not: a fund files quarterly or three times a year, one row per share class each time. Until 2026-08-31 the key discarded 72–77% of every published file on upsert, which is why FIP looked like a single 31-December row per fund. The key is now `(cnpj, doc_type, period, classe_cota, row_hash)`.

#### What the API will not do

- **No fabricated observations.** A missing month is absent, never interpolated or carried forward.
- **`as_of` ≠ `complete_through`.** The first is the newest row held, the second the last period believed complete. `coverage()` returns both.
- **Prices are unadjusted.** A split reads as a real ~50% jump. `adjusted` is `false` on every row.
- **1,000 rows per response, for everyone.** Signing in raises ids, page sizes and the query budget — never this.

### Keeping this honest

Add a dataset, add a row to §1. Decide against one, add a row to §2 with the reason. Ingest something the API does not expose, it belongs in §3 until it does. A table in none of the three sections is what this document exists to prevent.
