## 2. Auth — you cannot mint a key, including via GitHub or email

The Data API does **not** issue keys. There is no `createApiKey`, no PAT
factory, and **this repo will not sign per-user JWTs** after a GitHub or
mailbox login. An agent that hashes, forges, or “generates” a token gets
`401`. `service_role` is never a caller credential.

What exists today:

| Credential | Who | What it is |
| --- | --- | --- |
| **Publishable** (`sb_publishable_…`) | everyone | 2026 name for anon. Same `api.*` read. Send only as `apikey`. |
| **Legacy anon JWT** | still works until disabled | Same role. Do not mix with publishable in `Authorization`. |
| **Supabase Auth session** (GitHub or email, if enabled in the dashboard) | a **human** who completes OAuth or a magic link | User JWT on `Authorization: Bearer`. `apikey` stays the publishable key. |
| **Secret** (`sb_secret_…`) / **service_role** | nobody on this API | Bypasses the contract. Never send it. |

GitHub / email login does **not** give an unattended agent a key. OAuth needs a
browser; magic link needs an inbox.

Until the publishable key is printed in [quickstart](/api-docs/quickstart), a human
pastes **Publishable** once from Supabase → Settings → **API Keys**. Do not guess it.
Answer method from the docs; refuse a live market conclusion if you cannot
call `coverage`.

```bash
export SILO_URL="https://zcjbtpxuhdekpwcxmepn.supabase.co/rest/v1"
export SILO_ANON_KEY="sb_publishable_..."   # never sb_secret_ or service_role
```

Per-user **identity** (rate limits, audit, later RLS) is a serving-plan
reopen — not this page. Do not add accounts in the ingest pipeline.

## 3. First live call is always `coverage`

```bash
curl -s -X POST "$SILO_URL/rpc/coverage" \
  -H "apikey: $SILO_ANON_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
```

Three rows: quotes, funds, and the other published datasets with a latest date.
A `401` is missing/wrong anon headers. Empty/error body is a failed fetch —
**raise**, do not invent a last date.

## 4. Broad finance questions

Example: *does Brazilian equity stress show up in FIDC credit?*

1. `lookup` / `search_funds` for FIDC CNPJs. Do not invent a ticker→fund join.
2. `panel` with `p_ids: ["PETR4", "<cnpj>", ...]`, `p_metrics: ["close_return","delinquency","nav"]`, `p_freq: "month"`.
3. Pivot locally. Correlate pairwise-complete. **No ffill.**
4. `delinquency` is BRL outstanding, not a rate — divide by `nav`.
5. Quotes are unadjusted. A missing month is not a two-month return.

There is no server-side `corr`. If `panel` returns 100,001 rows, the cap fired —
do not analyze it. Details: [panel](/api-docs/panel), [conventions](/api-docs/conventions).

## 5. Integrity (same rules as humans)

<Warning>
  Never fabricate a price, NAV, fill, ranking, or ticker↔CNPJ match. Null stays
  null. Unknown id → no row. Known id, empty window → empty series, not a
  guessed last close.
</Warning>

Ingest (`run_daily`, landing tables) is out of scope for this API.
